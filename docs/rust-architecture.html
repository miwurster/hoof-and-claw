Hoof & Claw: Rust server architecture

1 · One tab's SSE stream

The tab opens GET /api/events. web subscribes to the Fanout before it builds the snapshot, so an event published in between arrives as an event and is never lost (ADR 0010). After the snapshot, the stream carries prices to every tab and a Player's own events to that Player's tabs.

  • A visitor without a Guess subscribes as the Player ID their first Guess will create, so the stream gets that Player's events from the first Guess on.
  • Prices go through a slot that holds only the newest price; Player events go through a bounded queue of 16, and a stream whose queue is full is closed instead of skipping one.
  • When the tab disconnects, the stream ends and frees its place in the per-IP stream limit.

2 · Crates as layers

Each layer may depend only on the layers below it, enforced by crate_graph_follows_the_table in crates/server/tests/architecture.rs. Only the crates named here may use tokio, sqlx, axum, tower-http or tokio-tungstenite, enforced by cargo-deny in deny.toml.

CORE: the game rules and their ports, synchronous, no I/O, no clock, no infrastructure at all
  • Within the core, identity depends on guessing, and guessing on prices.
  • bitstamp depends only on prices; sqlite on the cores; web and test-controls on game and the cores.
  • anyhow appears only in server.

3 · Crates as rings

The same crates seen from the inside out: the pure rules in the middle, game around them, and the adapters outside, each plugging into a port an inner ring owns. Every arrow points inwards.

  • A port is a plain trait named after the capability, and exists only where two implementations exist (ADR 0008).
  • game takes its adapters as generic parameters, never as dyn; there is no dependency injection container.
  • test-controls is compiled in only with the Cargo feature test-controls; the release build must not contain it.
